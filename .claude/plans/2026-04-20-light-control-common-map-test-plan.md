# 亮灯链路（CommonCountMap 口径）测试计划

## 1. 目标与原则
- 目标：验证 `upload / complete / control` 三条链路在“库位维度用户计数”下行为正确。
- 原则：**仅测试，不调整代码**；发现问题先输出问题报告（含复现、证据、影响）。

## 2. 测试范围
- 接口：
  - `/api/light/picking/upload`
  - `/api/light/picking/complete`
  - `/api/light/control`
- 关键能力：
  - `CommonCountMap` 计数正确性
  - 单用户/多用户分色正确性
  - 亮灭灯决策正确性
  - 重启后计数恢复正确性

## 3. 前置条件
- 使用固定波次：`WV202603250001`（或指定测试波次）。
- 确认日志级别包含接口内 `log.info` 输出。
- 测试开始前清理该波次历史测试数据（建议在测试库执行）：
  - `t_picking_upload`
  - `t_picking_upload_detail`
- 记录当前配置：
  - `stationCode`
  - `mixColor`

## 4. 测试数据
- 用户：
  - U1: `USER001`
  - U2: `USER002`
- 库位：
  - L1: `A1-11-02-01-01`
  - L2: `A1-11-01-01-01`
- 基础上报数据：
  - 两条明细覆盖 L1/L2，可调 `status`、`actualQuantity`。

## 5. 用例矩阵

### TC-01 单用户上传计数
- 步骤：
  1. U1 调用 `upload`，L1/L2 均未拣（`status=0`）。
- 预期：
  - `CommonCountMap` 中 L1/L2 均为 1。
  - upload 日志出现 `reconcile set(upload)`，`dbCount=1`。
  - 亮灯为单用户色（用户映射色或 GREEN）。

### TC-02 双用户叠加计数
- 步骤：
  1. 执行 TC-01 后，U2 用同波次同库位再调用 `upload`（未拣）。
- 预期：
  - L1/L2 计数升至 2。
  - 日志 `snapshot` 显示对应 key=2。
  - 亮灯走 multi user 分支，颜色为 BLUE（或控制接口内 multi 规则色）。

### TC-03 重复上报幂等（差量=0）
- 步骤：
  1. 同一用户、同一请求体连续调用 `upload` 两次。
- 预期：
  - 计数不异常累加（保持稳定）。
  - 不出现 `CommonCountMap: {}` 异常回空。

### TC-04 完成拣货后降计数
- 步骤：
  1. 在 TC-02 基础上，U1 对 L1 调用 `complete` 且达到已拣。
- 预期：
  - L1 计数从 2 -> 1（若仅 U1 完成）。
  - L1 若仍有未拣，继续亮灯但按单用户色。
  - `complete` 日志出现 `reconcile set/remove(complete)`。

### TC-05 完全拣完灭灯
- 步骤：
  1. U2 继续对 L1 调 `complete` 到全部已拣。
- 预期：
  - L1 计数归零并从 map 移除。
  - L1 出现在 turnOff 列表并触发灭灯调用。

### TC-06 控制接口 ON 模式
- 步骤：
  1. 对存在未拣库位的波次，调用 `control`（`mode=1/2`）。
- 预期：
  - 对用户未拣库位计数增量更新。
  - 单/多用户库位分组亮灯正确。
  - 非应亮库位触发灭灯（避免残灯）。

### TC-07 控制接口 OFF 模式
- 步骤：
  1. 调用 `control`（`mode=3/4`）。
- 预期：
  - 对用户未拣库位计数减量更新。
  - 计数归零库位灭灯；仍有用户库位按规则补亮。

### TC-08 应用重启恢复
- 步骤：
  1. 构造包含未拣数据的状态。
  2. 重启应用。
  3. 观察启动日志与首次请求行为。
- 预期：
  - 启动日志出现恢复结果（库位数与总计数）。
  - 重启后无需额外请求也能恢复 map 基线。

## 6. 通过标准
- 计数正确：每个库位的 map 计数与数据库“未拣 distinct bill_id”一致。
- 灯控正确：turnOn/turnOff 分组、颜色符合单/多用户规则。
- 稳定性：重复请求、重启场景无回空/漂移。
